# 6. 引入管理员手动失效接口

- 状态：已采纳
- 日期：2026-09-11
- 相关：缓存失效、运维手段、管理员接口

## 背景

自动失效的钩子（ADR 0002）**只覆盖经过应用的写入**。如果有人直接改数据库
（运维脚本、其它系统写同一个库、手工改库），应用根本不知道，缓存不会失效。

实测这个窗口有多大：**最大脏窗由 L2 的 TTL 决定，不是 L1 的**。
因为 L1 过期后会被 L2 里的旧值重新填满，所以「等 L1 过期」没有用。
更反直觉的是：**重启应用也救不了**——重启只清空 L1（JVM 内存），
Redis 里的旧值还在，第一次读又把它回填回来。

而运维侧当时**没有任何手段**清掉 L2：本机没有 `redis-cli`，
唯一的办法是手写脚本直连 Redis。

## 决策

**1）提供 `POST /cache/evict`，仅管理员可调用**
请求体 `{type, id}`，`type` 用枚举校验（picture / user，新增缓存区只需加枚举值）。

**2）粒度只做到单个 key**
不做「清空整个 picture 区」，也不做「全清」。

**3）总是返回成功（幂等），但返回各层实际清除情况**
`{localRemoved, redisRemoved, redisSkipped}`。

**4）每次调用记录审计日志**（操作人、目标、结果）。

## 被否决的替代方案

**用 Knife4j 的文档页当操作界面**
项目已有独立的 Vue 前端工程与现成的管理后台页面，界面由前端接入更合适；
后端只提供接口。另外「接口鉴权」才是安全边界——`static/` 下的页面本身无鉴权。

**支持清空整区 / 全清**
清空整区的 Redis key 不能用 `KEYS`（O(N) 阻塞命令，会卡住整个 Redis 实例），
必须用 `SCAN` 写游标遍历，还要处理遍历期间 key 变化。而且清空整区会让后续
**每个不同 key 各回源一次**，几千个 key 就是几千次数据库查询集中打过来。
精确删除是 O(1) 的 `DEL`，零风险、零额外实现（复用已有的 `evictPicture`/`evictUser`）。

**目标不存在时返回 404**
删除天然幂等，「目标 key 不存在」也算达成目标。返回 404 会让重复点击报错、
运维操作被「失败」提示打断。改为：成功返回 + 明细里体现各层实际情况，
这样既幂等，又能让管理员发现 id 写错（两层都是 false 说明该 key 根本没被缓存过）。

**不做审计**
审计日志的价值不止于追责，更重要的是**发现病根**：如果同一个 key 反复被手动清，
说明有写路径绕过了自动失效钩子。丢掉这条线索代价太大。

## 后果

**必须警惕的负面影响：这个接口会掩盖病根**
自动失效是「约定 + 机制」，而手动失效是一颗止痛药——「数据不对就点一下刷新」
会让症状消失，**真正的 bug 永远不会被发现**。这是引入本接口的主要代价，
在此明确记录，以免后来人把它当成常规操作。

缓解措施就是审计日志：**同一 key 反复出现 = 写路径漏网的明确信号**，
此时应当去查代码，而不是继续刷新。

**命名约定**
接口名用 `evict`（失效/删除），**不用 `refresh`**。
本接口只删不建，用 `refresh` 会误导调用方以为它会把数据重新加载进来。
「回填」是另一个动作，见 CONTEXT.md。

**与熔断的关系**
Redis 熔断期间调用本接口，`redisSkipped=true`：这次失效**没有**解决 L2 的脏数据，
需要在 Redis 恢复后重新执行。因此调用方不能只看 `code == 0` 就认为大功告成。

**安全边界**
- 鉴权依赖 `@AuthCheck`，它基于 **session 里的用户快照**：管理员被降级后，
  旧 session 在其有效期内仍然算管理员。
- `@AuthCheck` 依赖 Spring AOP，**必须从外部经代理调用**。
  实现时严禁在本控制器内部用自调用转发，否则会重蹈
  `UserController.getUserVOById` 鉴权被绕过的覆辙。
