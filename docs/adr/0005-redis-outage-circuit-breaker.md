# 5. Redis 故障期间的行为：熔断降级，并接受「失效可能没生效」

- 状态：已采纳
- 日期：2026-09-11
- 相关：二级缓存（L2）可用性、缓存失效
- 关系：本决策**为 ADR 0003 增加了一个前提限定**——0003 建立失效顺序时隐含假设
  「失效一定会成功执行」，本 ADR 明确该假设在 Redis 故障时不成立，并规定此时的行为。

## 背景

多级缓存的降级逻辑原本是「Redis 出错就捕获异常、继续查数据库、接口不报错」。
逻辑上没错，但**代价被低估了**：每次失败的 Redis 操作都要等满连接超时。

实测（用不可达地址模拟 Redis 虚拟机失联）：

| 场景 | 耗时 |
|---|---|
| `/api/health`（完全不碰 Redis） | 5ms |
| 图片详情，Redis 健康 | 12–29ms |
| 图片详情，Redis 不可达 | **6.0s ~ 15.6s** |

原因是：一个冷请求最多触发 **4 次** Redis 操作（图片读+写、作者读+写），
每次都要等连接超时。于是「缓存故障」被放大成「应用级雪崩」——
Tomcat 线程池会在十几秒内被耗尽，**接口从变慢升级成整片不可用**。

## 决策

**1）引入熔断器（自研，不引入 Resilience4j）**
连续失败 3 次后熔断，冷却 10 秒；冷却期内**直接拒绝访问 Redis，不再建立连接、不再等待超时**。
冷却结束后进入半开状态，**只放行一个探测请求**，成功则恢复，失败则重新熔断。
自研而非引入框架：逻辑只有一个状态机、约 100 行，引入依赖与配置的成本高于收益。

**2）把连接超时从 3 秒收紧到 1 秒，命令超时从 5 秒收紧到 2 秒**
对局域网 Redis 而言毫秒级建连即可完成，原来的值过于宽松，会成倍放大故障代价。

**3）明确接受一个副作用：Redis 故障期间的失效不会生效，且恢复后旧值会「复活」。**
故障期间 `deleteFromRedis` 被跳过或失败 → L2 里的旧值仍在 →
Redis 恢复后，下一次读会从 L2 拿到它并回填 L1，直到它的 TTL 到期。

## 为什么接受第 3 条，而不是做补偿

技术上可以做到：把失败失效的 key 记下来（内存队列 / 落库），Redis 恢复后重放。
但那会引入一套「失效补偿」机制——需要处理队列持久化、重放顺序、
重放期间的一致性、以及补偿本身的失败，复杂度远超收益。

而且**这个副作用不是熔断引入的**：熔断之前，删除同样会失败（只是要多等 3 秒超时），
结果完全一样。熔断只是把「已经失败且不会有结果」的操作提前放弃，并没有让一致性变差。

兜底手段有两条：
- L2 的 TTL（最长 30 分钟）——最终自愈，但有窗口；
- **管理员手动失效接口**——这是精确、即时的补救手段，也是该接口存在的核心理由之一。

## 后果

**好处**
- Redis 故障时，请求耗时从 6–15 秒降到 10–20 毫秒（实测）。
- 故障期间的日志量大幅下降：只在**状态切换**时输出，
  而不是每次失败的 Redis 操作都打一条带堆栈的 WARN。

**代价与必须知道的事**
- 熔断期间读路径**直接走数据库**，数据反而是新鲜的；问题只出在**写路径的失效**上。
- 半开探测意味着：每过一个冷却周期，**最多一个**请求会承担一次超时。
  这是刻意保留的「探测成本」，用极小的代价换取自动恢复能力。
- 熔断器的状态（`open` / 连续失败次数）已加入缓存状态快照，
  一旦出现 `open=true` 说明缓存已完全退化为直查数据库，**数据库压力会明显上升**。

**验证方式**
- 状态机（闭合 → 熔断 → 半开 → 恢复 / 探测失败重新熔断）用直连测试程序逐条断言验证，
  12 项全部通过。
- 端到端：用不可达地址启动，冷请求耗时从 6.0s 降到 12ms（实测）。
