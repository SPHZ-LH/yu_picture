# 积分：余额在 user 表原子增减，流水表兼任幂等护栏

扩图弹窗「每次消耗 10 积分」落地为：`user.points`（权威余额，原生 SQL 原子增减）+ `points_log`（每笔一行：delta/balance/reason/relatedId）。变动顺序固定「先改余额、后写流水」，流水唯一键 `uk_reason_relatedId` 兼任**退款幂等护栏**。规则常量在 `PointsConstant`（注册赠送 100 / 扩图消耗 10），原因枚举 `PointsReasonEnum`（register/admin/outpainting/outpainting_refund）。词条见根 CONTEXT.md「积分 / 积分流水」。

**Considered Options**

- 只加 user.points 不留流水：省一张表，但失败退款无法幂等（怎么知道这笔任务扣没扣、退没退）、管理员调整无从对账。
- 余额由流水聚合算出（不存余额列）：绝对一致，但每次查余额都要 SUM 全量流水，而余额是扩图门槛的高频读。冗余余额 + 流水对账是标准账务折中。

**Consequences**

- **扣分时序：查余额 → 提交任务 → 扣分**。提交失败不扣分；查与扣之间有竞态窗口（余额刚好被别处花掉），此时任务已在百炼侧创建，放弃任务的代价大于送出 10 积分——放行并 WARN，不追回。该任务没有扣分流水，失败退款时查不到流水自然不退，逻辑自洽。
- **退款幂等**：扩图任务查询到 FAILED 时退还。同一 taskId 的退款行受唯一键保护，并发退款只有一个能写入流水，另一个回滚变动后按「已被处理」返回；先查后插只是省一次无用变动，真正护栏是唯一键。
- **余额守卫在 SQL 里**：`UPDATE ... SET points = points + ? WHERE points + ? >= 0`，并发扣减不可能透支；管理员负向调整同理（「调整后积分不能为负」）。
- **积分不进 UserVO 缓存**：余额变更绕过多级缓存直接改库，与 downloadCount 同一处理（docs/adr/0002），无需失效用户缓存。
- **获取途径当前只有注册赠送与管理员调整**：签到/任务等获取方式是后续拓展；流水表已按可扩展原因设计，加枚举值即可。
