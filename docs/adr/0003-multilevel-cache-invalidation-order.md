# 3. 多级缓存的写路径：失效顺序与时机

- 状态：已采纳
- 日期：2026-09-11
- 相关：图片/用户缓存失效、二级缓存（L2）引入
- 延伸：本决策**扩展** ADR 0002（缓存读写边界），不推翻它——失效钩子的位置不变，
  但钩子内部的行为从「清一层」变成「按确定顺序清两层」。

## 背景

引入 L2（Redis）后，一次写入要清的不再是一层，而是**本机 L1 + Redis L2**。
写入点分散在 9 处（图片 5、用户 4），均已被 ADR 0002 的 override 钩子收敛。

关键问题：**清两层的顺序是否重要？** 直觉上不重要——两层都删掉，先进后进有什么区别。
但并发存在时它是有区别的。

## 决策

**1）失效必须在数据库写入成功、且事务提交之后发生。**
当前项目没有 `@Transactional`，`updateById` 返回时已自动提交，所以钩子里紧接着失效是安全的。

**2）清两层的顺序固定为：先删 L2，再删 L1。**

**3）失效动作是删除，不是「用新值覆盖缓存」。**

## 为什么顺序重要

设「写库已完成」为起点，此时恰好有一个并发读进来：

- **先删 L1、后删 L2**（错误顺序）：该读在 L1 未命中 → 去 L2 读到**旧值**
  → 把旧值**回填进 L1**。等我们再删 L2 时已经晚了，
  **L1 里躺着旧值，会一直脏到 L1 的 TTL 过期**。
- **先删 L2、后删 L1**（正确顺序）：该读在 L1 命中旧值，只返回**一次**旧数据（微秒级窗口），
  **L1 不会被污染**；随后 L1 被删，下一次读一路回源拿到新值。

差别是「只脏一次」对比「脏到 TTL」。

## 被否决的替代方案

**写库后只删 L2，L1 靠短 TTL（10–30 秒）自然过期**
写路径更简单，不需要碰本地缓存。但编辑后最长一个 L1 TTL 内用户看到旧值；
在**删除**场景下这个代价无法接受——用户看到的是「删了还在」。

**两层同时删，不关心先后**
代码最短。但存在把旧值回填进 L1 的风险，一旦命中就是脏到 TTL 而非脏一瞬间。

**用新值覆盖缓存而非删除**
并发写会互相覆盖，留下永久脏数据且不报错。明确否决。

## 后果

**好处**
- 并发下的旧值暴露被限制为「最多一次读」，而不是「持续到 TTL」。
- 失效顺序被固化，未来若有人为了「优化」把两次删除并行化，会静默重新引入该缺陷——
  这是写下本 ADR 的主要理由。

**约束（实现时必须落实）**
- 若将来给 `*ServiceImpl` 的写方法加上 `@Transactional`，
  **失效逻辑必须移到事务提交之后**（事务同步回调或事务事件监听），
  否则会变成「事务内的旧值被并发读回填」。
- L2 降级时（Redis 不可用），写路径退化为**只删 L1**，删除 L2 的失败被忽略并记日志。

**残留风险**
- 钩子的完备性仍依赖「所有写入都走标准 CRUD 方法」这一前提（见 ADR 0002）。
  L1 与 L2 的 TTL 是该前提失效时的唯一兜底，因此两者都必须有限。
