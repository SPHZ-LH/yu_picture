# 下载日志与榜单：事件表 + 滚动窗口，不做快照表

榜单（日/周/月）、排名趋势（↑↓/新上榜）、用户下载历史、创作者下载聚合，全都出自同一张事件表 `picture_download_log`：每次下载追加一行（pictureId、userId、createTime），不去重、不回改。下载入口在 `PictureController#downloadPicture`：计数自增后、重定向前记一条日志；写日志尽力而为，失败只 WARN，绝不影响已完成的下载重定向。词条见根 CONTEXT.md「下载日志 / 下载榜单 / 榜单周期 / 排名趋势」。

接口两个：`POST /picture/ranking`（匿名可访问，body：period/category/分页，返回图片视图 + 窗口内下载量 + 名次 + 趋势）；`POST /picture/download/history/my`（登录，按下载时间倒序的本人历史）。首页「本周最受欢迎」复用 ranking（period=week）。

**Considered Options**

- 预聚合快照表（每天 0 点定时把各榜单算好写库）：查询最快、能精确表达「每天 0 点更新」，但要多一张表 + 定时任务 + 手动补数路径。当前量级（百张图、窗口内下载百次量级）实时聚合毫秒级完成，「每天 0:00 更新」由前端文案表达即可。
- 在 picture 表加 dailyDownloadCount 每天 0 点清零：省一张表，但只有「今日」没有周/月，且清零后永远失去回溯能力——趋势（相对昨天）就没法算了。

**Consequences**

- **周期是滚动窗口不是自然日**：日榜=近 24 小时、周榜=近 7 天、月榜=近 30 天。与「每天 0 点更新」的直觉有偏差，但换来的实现简单是当前量级下正确的取舍；将来真要严格自然日再切快照表。
- **趋势以上一等长窗口下载量前 100 名为基准**：前 100 内有名次的按名次差给 up/down/flat，无名次一律 new（新上榜）。上一窗口排在 101 名之后升上来的图会被误标为新上榜——榜单展示前 15 名，影响面可忽略。
- **榜单只算公共图库过审图**：SQL 里 JOIN picture 过滤 `spaceId IS NULL AND reviewStatus=1 AND isDelete=0`。空间图片不参与排名；图片被删后榜单与历史条目自然消失。
- **下载历史不做可见性复查**：只要求图片记录还存在。用户下载当时对该图可见，历史记录的是已发生的事实；收藏列表的可见性过滤（编辑后重回待审核会消失）不适用于这里。
- **日志表无 isDelete、暂不清理**：当前量级没有归档压力；量起来后按窗口加归档策略（如保留 13 个月供月榜回溯）。
- **排名并列用 pictureId 倒序**：保证翻页时排序稳定。
- **趋势查询 `Page(1,100,false)` 关闭 count**：趋势名次表只是附属信息，不值得为它跑一次 COUNT。
