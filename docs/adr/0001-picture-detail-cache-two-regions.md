# 1. 图片详情缓存拆成两个独立缓存区（picture / user）

- 状态：已采纳
- 日期：2026-09-11
- 相关：图片详情查询（按 id 暴露单张图片视图）

## 背景

要为**图片详情**查询引入 Caffeine 本地缓存，前提是单实例部署、且图片详情的内容
**不随访问者变化**（作者信息已脱敏，无密码字段），因此缓存可以用单维 key（图片 id）。

一张图片详情由两部分拼成：**图片自身字段** + **作者信息**（内嵌 `UserVO`）。
需要决定缓存条目里装什么。

关键约束：**Caffeine 不支持按 `userId` 批量淘汰。**
如果缓存条目里包含了作者信息，那么当某个用户被修改后，要清掉「所有作者是该用户的
图片缓存」，就必须自己维护一张 `userId → Set<pictureId>` 的倒排索引。

## 决策

拆成**两个互相独立的缓存区**：

- `picture`：图片 id → 图片自身数据
- `user`：用户 id → 作者视图

读取时先各自取缓存、命中不了的分别回源，然后组合成图片详情返回。

## 被否决的替代方案

**缓存完整图片详情（含作者）**
命中即可零次查库，性能上限最高。但用户改动后，缓存里的作者信息只能等 TTL 自然过期，
或者被迫自建上述倒排索引——为了一个低频的改名动作维护一张索引，不划算。

**只缓存图片自身，作者每次实时查库**
失效逻辑最干净（只按图片 id 清），且用户改动天然不会污染图片缓存。
代价是每次命中仍要一次用户查询，查询次数只从 2 次降到 1 次，收益减半。

## 后果

**好处**
- 两个缓存区**失效职责完全不交叉**：图片写入只清 `picture`，用户写入只清 `user`。
  不需要任何跨实体的索引或关联。
- 不需要为「用户改动」设计任何特殊机制。

**代价**
- 命中时是**两次缓存查找 + 一道组合逻辑**，而不是一次。
- 两个缓存区需要**分别**配置 TTL 与容量。
- 组合逻辑成为一处必须维护的组装点。

**需要注意的正常情况**
- **部分命中是常态**，不是异常：图片命中但用户未命中时，只回源查用户即可，
  不需要把已经命中的那部分也丢弃重来。
