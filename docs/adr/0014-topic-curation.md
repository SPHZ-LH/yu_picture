# 专题：编辑维护的合集，入选资格在写入时校验、查询时兜底

屿图「专题」板块（首页精选专题三卡 + 专题列表页 + 本周精选 hero）由新实体 `topic` 与关系表 `topic_picture` 支撑：专题有名称/简介/封面/分类/策划人/更新节奏文案，「本周精选」是全站唯一位置。管理端五个接口（增删改 + 图片加入/移出），公开端四个（列表/精选/详情/专题内图片分页）。词条见根 CONTEXT.md「专题 / 专题入选」。

**Considered Options**

- 图片打专题标签（picture.tags 里加 `topic:xxx`）：零新表，但标签词表是 AI 预填与筛选器的取值域，把「编辑策划行为」混进「图片内容属性」会让两边都变脏；专题还带封面/策划人/更新节奏这些自己的属性，标签装不下。
- 关系表在查询时校验资格（不在写入时拦）：写入放得更宽，但脏关系会静默存在，专题页靠 JOIN 过滤只是「看不见」不是「没进错」——计数与详情会出现对不上的诡异状态。写入时校验 + 查询时兜底两层都要。

**Consequences**

- **精选位互斥由服务层保证**：设置 isFeatured=true 时自动清掉其他专题的精选位。数据库层不设「至多一条」约束（MySQL 没有部分唯一索引），并发下理论上可能出现双精选，展示端取最新一条兜底。
- **专题计数是实时子查询**（公共图库过审口径）：专题量级小（≤ 百），不缓存不加冗余计数列；图片被移入空间/下架/删除后自动从计数与专题页消失。
- **策划人是可选外链**：curatorId 传了必须指向真实用户；展示名从用户表实时取，用户改名后专题页自动跟随。
- **专题删除是逻辑删**，topic_picture 关系行保留（孤儿行对查询不可见）；重建专题是新 id，旧关系不复活。
- **更新节奏是自由文案**（「每周五更新」）：是编辑承诺不是系统能力，后端不做定时换血；「本周精选」的轮换由管理员手动改。
