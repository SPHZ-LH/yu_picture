# AI 预填图片信息：读图只产出建议，人确认才落库

上传后要给图片填名称/简介/分类/标签，这一步改由读图模型完成（默认 `qwen-vl-plus`，走百炼 OpenAI 兼容端点）：新建上传完成即自动预填表单，编辑页由「AI 重新读图」按钮显式触发。**AI 不写库**——落库仍走 `/picture/edit`，人看着改完点保存（词条见根 CONTEXT.md「AI 预填」）。接口 `POST /picture/ai/prefill` 只收图片 id，地址由后端按 id 取，不接受客户端传 URL（与扩图保存同一条纪律）。

**Considered Options**

- 直接落库（上传即由 AI 写死信息）：省一步确认，但分类与标签是筛选器的取值域，写错不是"这张图信息不好看"而是污染全站检索；读图模型有错率，而确认成本只是瞟一眼。
- 允许 AI 造新标签/新分类：标注会更贴画面（实测模型爱回"梦幻/海底/云海"这类词），但词表会被撑散，筛选器里冒出一堆只有一张图用的选项。词表扩不扩由人定，不交给模型。

**Consequences**

- **模型可换且写在配置里**：`ai.vision.{model, path, baseUrl, apiKey, timeoutMs}`（配置类 `AiConfig`，块按**用途**分——`ai.outpainting` 在百炼、`ai.vision` 在 DeepSeek，块名不绑厂商）。换模型改一行；换供应商填 `baseUrl` + `apiKey`，两者**必须成对**；都留空则复用 `ai.outpainting` 那一套（两家都用百炼时的快捷路径）。不做"后台界面运行时切换"：多一套读写配置的接口与权限，一年用不上几次，改配置重启更快。
  - **2026-09-25 切到 DeepSeek**：用户要求换成 `deepseek-flash`（它家带 Vision 的模型，`deepseek-v4-pro` 不支持图片）。实测 `deepseek-flash` 在百炼域名下 `model_not_found`，所以这不是改模型名而是换供应商 → `baseUrl: https://api.deepseek.com`、`path: /v1/chat/completions`。
  - **换供应商必须单独配 Key**：`vision.baseUrl` 非空而 `vision.apiKey` 为空时，代码**宁可不调也不回退**——拿外层百炼 Key 去调别的厂商域名等于泄露凭据，比功能不可用严重得多。这时记一条 ERROR 日志说明原因，接口返回空（前端按"没读出内容"处理）。Key 本身走环境变量（`${DEEPSEEK_API_KEY:}`），不写进配置文件。
  - **超时必须随供应商重标**：同一条链路实测 `qwen-vl-plus` 1.1~1.6 秒、`deepseek-flash` 3.3~6.5 秒。原先按前者定的 5 秒超时在切到 DeepSeek 后 **4 次里 3 次 SocketTimeout 静默失败**（日志有 WARN，接口返回空）——静默失败在这里反而掩盖了真正的问题：不是模型不行，是超时定得太紧。现取 15 秒（约 2 倍余量）并实测 3/3 成功。换模型/供应商时把这条一起标定。
- **必须是视觉模型**（最坑的一条）：实测同 Key 下 `qwen-vl-plus` / `qwen-vl-max` / `qwen3-vl-plus` 可用；而文本模型 `deepseek-r1` / `deepseek-v3` **收到图片既不报错也不看图**，回一句"我无法查看图片"后凭文本瞎编一组信息——静默失败比报错难查。未开通的模型名返回 `access_denied`，该错误原样进日志，不当成"没读出内容"吞掉。
- **三道护栏**：
  1. 严格 JSON（`response_format: json_object`，只清 BOM/空白）：解析不出来整体丢弃，绝不从散文里抠字段；
  2. 词表封闭：分类必须命中分类词表、标签只在标签词表内挑（去重、最多 5 个），越界即丢；词表唯一定义在 `PictureInfoConstant`，前端选项接口、提示词、结果校验读同一份，避免三处漂移；
  3. 失败静默：默认 5 秒超时，异常/超时/无可用字段一律返回空，上传流程一个字不受影响；日志记模型名、耗时、tokens（视觉模型的输入含图片折算额度，纯文本模型这个数会明显偏小，是"没看图"的线索）。
- **覆盖规则**：自动预填不覆盖人已手填的字段，但覆盖上传时派生的文件名占位名（`wallhaven-3z32j3` 这种对人没有信息量）；编辑页那个按钮点了就是明确要覆盖表单，按钮文案照实写。
- **数据出域事实**：预填会把图片的 COS 地址交给模型服务方去读。库里都是上传者自己的图、用的是自己的 Key，不构成额外授权问题；将来换供应商或多用户化时要重新评估这一条。
- **存量图片批量补全暂不做**：新上传这条线已覆盖增量，存量是百张量级，一次性人工处理成本不高，而批量补全要额外解决确认与回滚。真要做时形态应是"只填空字段 + 管理员触发 + 逐条留痕"。
