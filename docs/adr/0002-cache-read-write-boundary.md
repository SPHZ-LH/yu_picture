# 2. 缓存的读写边界：写侧 override 框架方法，读侧用专用组合方法

- 状态：已采纳
- 日期：2026-09-11
- 相关：图片与用户的缓存失效、图片详情读取

## 背景

确定用两个 Caffeine 缓存区之后，需要决定**缓存代码挂在哪里**。

写入侧的困难是**写入点分散且不集中**：图片有 5 个写入点、用户有 4 个写入点，
其中大多数是 controller 直接调用 MyBatis-Plus 框架方法（`updateById` / `removeById`），
**完全绕开任何自定义 service 方法**——所以「把失效逻辑写在一个 service 方法里」
这条最省事的路走不通。

读取侧存在一个陷阱：**`getById` 的结果被用于鉴权判断**。
上传图片前的「图片是否存在」校验和「是否本人或管理员」判断，都读的是 `getById` 的返回值。
把缓存埋在这一层，鉴权就会变成缓存依赖——缓存一脏，鉴权可能放错人。
而且 `getById` 是框架方法，内部调用者众多，把缓存塞进去会让影响面无法静态推断。

## 决策

**写侧：在 `*ServiceImpl` 里 override 框架写方法，作为统一失效钩子。**
覆盖 `save` / `saveOrUpdate` / `updateById` / `removeById` 这一组标准方法，
在 override 内部调用父类实现后清除对应缓存。

**读侧：新增专用的组合方法（如按 id 取图片详情），缓存只存在于该方法内部。**
**绝不缓存 `getById` 等框架查询方法。**

## 为什么写侧可行

已逐个核对全部写入点，**没有任何一处直接调用 `baseMapper` 做写入**
（`baseMapper` 仅用于 `selectOne` 读取）。图片的 5 个写点、用户的 4 个写点
全部经过上述可 override 的方法，其中两处 service 内部调用是虚分派，同样会命中 override。
因此该钩子是严密的，没有绕过路径。

## 被否决的替代方案

**在每个写入口逐个挂 `@CacheEvict`**
最直白易读，但失效逻辑散落 9 处；将来新增写接口极易遗漏，而遗漏的后果是**永久脏数据**
（只能等 TTL 自愈）。

**完全不写显式失效，只依赖 TTL**
改动量最小，但删除图片后，被删图片会在最长一个 TTL 内继续正常返回给用户——
这不是毫秒级脏读，是用户能明确感知的「删了还在」。

**缓存 `getById`**
能覆盖所有读路径，但会把鉴权判断变成缓存依赖，并污染框架内部调用语义。已否决。

## 后果

**好处**
- controller 的写侧**零改动**。
- 失效逻辑**单点收敛**，不需要在 9 个地方重复。
- 将来新增的写接口，只要走标准 CRUD 方法就自动被覆盖。

**必须遵守的约定（重要）**
- 若将来改用 **`update(Wrapper)` / `removeByIds` / `saveBatch` / `updateBatchById`**
  等未被 override 的方法写图片或用户，**失效会被漏掉**。
  该约定必须写入 `*ServiceImpl` 的代码注释。
- override 框架方法会带来**看不见的副作用**：后来人读 `updateById` 的调用点时
  不会预期它有缓存副作用。这是本决策的主要认知成本，靠注释与本 ADR 传达。

**残留风险**
- 钩子的完整性依赖「所有写入都走标准 CRUD 方法」这一前提。
  TTL 过期机制是本前提失效时的唯一兜底，因此 **TTL 不能设为无限**。
