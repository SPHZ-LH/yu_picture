# 关注 / 喜欢 / 收藏公开：三套关系各自独立，物理删除 + 唯一键幂等

社交三件套一次成形：**关注**（user_follow，用户对用户）、**喜欢**（picture_like，用户对图片）、**收藏公开开关**（user.collectPublic）。三者语义刻意分开——收藏是个人存档（collect 已有），喜欢是内容认可，关注是人的订阅；不做互相推导（喜欢≠收藏、关注≠粉丝）。词条见根 CONTEXT.md「关注 / 粉丝 / 喜欢 / 获赞 / 收藏公开」。

**Considered Options**

- 合并喜欢与收藏为一张表加 type 列：省一张表，但两者的可见性、列表、批量状态接口全都不同（收藏可进公开主页、喜欢不进；收藏有计数列、喜欢没有），合表后每个查询都多一层 type 过滤，得不偿失。
- picture 表加 likeCount 冗余列：设计稿只需要「获赞总数」聚合与本人点赞列表，没有单图点赞数展示；等 UI 真要显示再加列回填。

**Consequences**

- **取关/取消点赞都是物理删除**（同 collect 的取舍）：逻辑删会撞唯一键导致无法重新关注/点赞。重复关注/点赞的并发冲突用 DuplicateKeyException 捕获按幂等成功处理。
- **点赞的写入门槛是图片当前可读**（checkPictureReadable），但**获赞数只过滤未删除**——历史认可不因图片后来下架/回审而消失；「我的喜欢」列表则按收藏列表同款可见性 JOIN 过滤（编辑后重回待审核的图会暂时消失）。
- **收藏公开是用户级开关**（user.collectPublic，默认关）：公开主页的收藏 tab 按 UserVO.collectPublic 决定是否渲染；列表接口在未开启时返回空页而非报错。空间图片无论开关都不公开——公开收藏只含公共图库过审图。
- **粉丝数批量走 GROUP BY**，不冗余计数列：创作者列表一页 ≤ 30 人，一次分组查询足够；量级起来后再考虑计数表。
- **关注/喜欢状态批量接口匿名可访问**（未登录返回全未关注），与星标批量的既有约定一致：附属状态不该让整页请求失败。
