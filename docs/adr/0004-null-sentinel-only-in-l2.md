# 4. 空值哨兵只落在 L2，L1 保持无空值

- 状态：已采纳
- 日期：2026-09-11
- 相关：缓存穿透防护、多级缓存分层
- 影响：**修改**了单层缓存时期「两层都不缓存空值」的结论

## 背景

在只有 L1（本地缓存）时，本项目明确否决了「缓存空值防穿透」，理由有两条：

1. 本地缓存库**不接受 null 值**，要缓存「不存在」就必须把值类型改成 `Optional` 之类的包装，
   **所有条目的读写都要跟着拆包**。
2. 图片 id 由雪花算法生成（19 位），随机撞中真实 id 的概率极低，
   穿透的实际威胁有限。

引入 L2（Redis）后，**第 1 条理由在 L2 上不再成立**：Redis 本来就以字符串存储，
塞一个哨兵标识几乎没有额外成本，也不必改变任何值类型。
于是出现了一个在单层缓存时期**不可能存在**的选项。

## 决策

**「图片不存在」这一事实只在 L2 用空值哨兵缓存，配一个短 TTL（60 秒）。
L1 不缓存空值，其值类型保持为不含空值语义的 `Cache<Long, 图片>`。**

## 为什么这样切

三层各自的代价并不相同：

- 把哨兵放进 **L2**：成本极低（一个字符串，不改类型），却能把「无效 id」从
  **每次都打数据库**降到**只打一次 Redis**。这是性价比最高的一层。
- 把哨兵放进 **L1**：需要把值类型改成包装类型，**所有读写路径都要拆包**——
  用全局的类型复杂度换一层本来就已经很便宜的拦截，不划算。

## 被否决的替代方案

**两层都不缓存空值（维持旧结论）**
逻辑最简单、没有哨兵概念。代价是恶意刷无效 id 时每次都落到数据库。
在有了 L2 这个低成本拦截点之后，放弃这个便宜的防护已无正当理由。

**两层都缓存空值**
防护最彻底（连 Redis 都不打）。代价是 L1 的值类型被包装类型污染，
所有读写都多一道拆包，为一个低频攻击面付出全局的类型复杂度。

## 后果

**必须注意的反直觉点**
- **L1 与 L2 对「空值」的行为刻意不对称**：L2 会存「不存在」，L1 不会。
  后来人很可能会觉得这是疏漏而「顺手统一」——**统一到任意一边都会破坏本设计**：
  统一到 L1 会污染类型，统一到 L2 会丢掉穿透防护。改动前请先读本 ADR。
- 哨兵值必须与真值**可区分**，且反序列化后仍能识别。哨兵 TTL 要短，
  避免「暂时查不到」被长期固化成「永远不存在」。

**残留风险**
- 被缓存为「不存在」的 id，在 TTL 内即使数据后来出现也会继续被判定为不存在。
  当前 id 由 `IdType.ASSIGN_ID` 在插入时生成、客户端无法指定，
  因此「不存在」实际上是不可逆的，该风险不构成实际问题。
