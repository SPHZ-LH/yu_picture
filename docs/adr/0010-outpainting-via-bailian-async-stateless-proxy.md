# 画面扩展走百炼异步任务，后端做无状态代理

画面扩展（Outpainting，见根 CONTEXT.md 词条）用阿里云百炼 `image-out-painting`：异步两段（submit 拿 taskId、轮询 task 拿结果 URL）、按张计费、QPS 2 / 并发 5。后端**不持有任务状态**：`/picture/expand/submit` 转发创建并返回 taskId，`/picture/expand/result` 转发查询，前端 3s 轮询、上限 2 分钟（taskId 存 sessionStorage，刷新后可续轮询）；`/picture/expand/save` 只收 taskId，由后端重查任务取结果 URL 再下载写 COS——不接受客户端传入 imageUrl，杜绝伪造外链写入图片记录。扩展产物沿用编辑保存语义（新 objectKey、记录改指向、公共图重审）。

**Considered Options**

- 服务端同步轮询后返回：单请求挂数十秒占 Tomcat 线程，QPS 2 之下一点小并发就能耗尽线程池，把计费服务的故障升级成应用级雪崩——与 ADR 0005 熔断器防的是同一种形状的风险。
- 任务表 + 后台线程轮询：任务本身 24h 有效、前端轮询窗口只有 2 分钟，持久化换不来收益，只换来清理负担。

**Consequences**

- 接入域名：v1 上线时用通用域名 `dashscope.aliyuncs.com`（2026-09-20 实测受理该模型、无需 WorkspaceId）；**2026-09-25 迁至业务空间专属域名** `ws-rz37gsunxmj7700a.cn-beijing.maas.aliyuncs.com`——官方口径通用域名属存量兼容、2026-09-30 起不再支持新特性（[选择地域与接入域名](https://help.aliyun.com/zh/model-studio/regions)）。迁移实测行为完全对齐：同一 Key 在两域名的路由/鉴权响应一致，16:9 双域名均 SUCCEEDED，21:9 双域名同样 FAILED。只换 baseUrl 即可，请求路径与 header 不变（专属域名 region 必须与 Key 一致，否则 401）。
- 宽高比两条路：**白名单内的比例走 `output_ratio`，白名单外用像素偏移**。服务端白名单实测只有 `['', '1:1', '3:4', '4:3', '9:16', '16:9']`——2026-09-25 传 `16:10` 被异步拒绝，原文把可选项原样列出：`the output_ratio(1.0) is error, please choose one from ['', '1:1', '3:4', '4:3', '9:16', '16:9']`；`21:9` 同样是异步 `InvalidParameter`（新老域名报错一字不差，属 v1 起就带的缺陷）。设备屏幕常见的 16:10 / 19.5:9 都不在白名单里，**但四边偏移不受白名单约束**：`top_offset`/`bottom_offset`/`left_offset`/`right_offset` 是"在指定方向补像素"，据此把画布补成任意比例——2026-09-25 实测 3640×2048 传 `top 113 / bottom 114` → **3640×2275，精确 16:10**（`OutPaintingManager#fillOffsetParameters`：偏移只能加不能减，所以永远沿需要变长的那条边补；单轴合计超过 3× 输入边长按官方上限拒掉）。因此固定档位仍走 `output_ratio`（路径最短），"我的屏幕"落在白名单外时自动改走偏移，前端不再有"扩图不支持"的死路。
- **两种模式共用同一条拒绝规则**：目标画幅不能与原图相同。`output_ratio` 模式下服务端判 `InvalidParameter.ImageResolution`，偏移模式下由我们在提交前按 0.1% 容差拦掉，避免白跑一单。
- 账户欠费（`Arrearage`）等错误码由后端映射为中文消息；欠费结清前真实出图不可用。
- **目标画幅不能与原图相同**：服务端 submit 受理，但任务在 ~1 秒内判 `FAILED`，`output.code=InvalidParameter.ImageResolution`、message 为 "When the input parameter contains output_ratio, the aspect ratio of the input image cannot be equal to the output aspect ratio"（2026-09-25 实测，1920×1080 的图传 `output_ratio=16:9`）。也就是说给一张已经是 16:9 的图选 16:9 是必然失败的一单。**2026-09-25 定的默认值规则**：默认画幅 = 设备屏幕比例命中的那一档（见 CONTEXT.md「设备屏幕比例」），命中但与原图同比例、或五档都不命中时不预选，由用户另选；与原图同比例的档位在页面上置灰并标注「已是当前画幅」，未选画幅时提交按钮不可用。原先写死的 `16:9` 默认值就此废弃——它对 16:9 的原图是个必败组合。
- 服务端 `FAILED` 不抛异常（走 `output.code`），原先只在日志外静默映射文案，排查时日志里什么都看不到——2026-09-25 补了 `扩图任务失败` ERROR 日志（taskId + code + message）。
- **提交时显式传 `add_watermark: false`**（2026-09-25 修）：该参数官方默认 true，会在输出图**左下角**打 "Generated by AI" 水印（[图像画面扩展 API](https://help.aliyun.com/zh/model-studio/image-scaling-api)）。水印是模型直接烧进像素的，不是可后处理掉的图层——已产出的带水印图片只能拿干净原图重新扩一次，别指望裁掉左下角。合规上如需声明 AI 生成，应由本应用自己的展示层负责，不依赖模型水印。
- 刷新且 sessionStorage 丢失时进行中的任务成为孤儿（仍会计费、结果无人取），属接受内的成本上限：单张 0.18 元。
